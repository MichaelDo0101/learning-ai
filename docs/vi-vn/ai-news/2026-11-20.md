Về phương pháp huấn luyện: dùng AsyncGRPO từ TRL với 8 rollout mỗi task ở nhiệt độ 0,8, trên 750 task scale800 xen kẽ 300 task TermGrade; phần thưởng gồm tính đúng của verifier cộng thưởng hiệu quả công cụ với trọng số 0,1; giới hạn 50 bước agent và 1.800 giây mỗi rollout, tắt thinking. Kết quả tự báo cáo (harness pi, 1 lần thử mỗi task): adapter giải thêm 15 task SWE-bench Pro và mất 2, trên Terminal-Bench 2.1 được thêm 16 và mất 2; điểm trung vị số lượt để giải được task trên cả hai benchmark giảm từ 59 xuống 23 (SWE-bench Pro) và từ 18 xuống 8 (Terminal-Bench 2.1). Điểm mạnh lớn nhất là hiệu suất: adapter sinh khoảng 4,5 lần ít token hơn bản gốc bật thinking, và với thinking tắt nó đạt độ chính xác tương đương bản gốc bật thinking (64,7% SWE-bench Pro, 54,2% Terminal-Bench 2.1), với bật thinking thì đạt 66,7% và 56,6%. Triển khai: vLLM với `--enable-lora --max-lora-rank 32` và tắt thinking, llama.cpp với adapter GGUF trên nền Q8_0, Llama.app trên macOS với context 32.768 token, hoặc merge bằng PEFT trên CPU thành checkpoint BF16 khoảng 54 GB — nhờ adapter dùng chung một base model, một server có thể phục vụ adapter cho pi và OpenCode song song. * **Meta FAIR công bố "Self-Improving Memory" — Kimi-K2.6 tự viết prompt quản lý bộ nhớ rồi nén năng lực đó vào trọng số, đạt 56,0 điểm trên Continual Learning Bench so với 44,6 của harness viết tay tốt nhất:** Ý tưởng trung tâm là agent quản lý bộ nhớ dạng file qua hai prompt — OFFLOAD (cập nhật bộ nhớ sau mỗi subtask) và LOAD (truy xuất ghi chú trước subtask sau) — nhưng thay vì dùng prompt cố định, một meta-agent sẽ tự viết lại chính hai prompt đó. Giai đoạn 1 bắt đầu từ 4 prompt viết tay làm seed (Summary, Retrieval, Skill, Hypothesis), mỗi ứng viên chạy 5 lần toàn bộ chuỗi task, top 4 theo điểm trung bình làm cha để meta-agent đọc trajectory, chấm điểm và đề xuất bản sửa; chọn lọc dùng một tập holdout mà meta-agent không nhìn thấy. Giai đoạn 2 là pipeline Discover-Demonstrate-Distill: ghi lại toàn bộ lệnh model, thay prompt tối ưu bằng prompt generic trong lịch sử đó (điều này khả thi vì hành vi vẫn hợp lệ dưới chỉ dẫn chung), rồi fine-tune bằng LoRA rank 64 trên các projection của lớp attention, loss chỉ tính trên token của assistant (bao gồm reasoning và tool call). Kết quả trên 3 task Continual Learning Bench (Database, Codebase, Spectrum) với Kimi-K2.6 — base model MoE 1 nghìn tỷ tham số, 32 tỷ active, context 256K: không có memory đạt 20,4 điểm trung bình; compaction 37,1; harness generic 36,1; harness viết tay tốt nhất 44,6; harness tối ưu 56,0 (Database 53,8; Codebase 64,3; Spectrum 49,9). Điểm đáng chú ý nhất về kỹ thuật: sau khi nén vào trọng số, model chạy lại với harness generic trung bình 43,1 điểm — tức là kỹ năng quản lý bộ nhớ đã thực sự nằm trong trọng số chứ không còn phụ thuộc prompt. Điểm cần nói rõ: hiệu quả vẫn kém prompt tối ưu (56,0 so với 43,1 sau nén), quá trình tìm prompt rất nhiễu (37 trong số 44 bản sửa không vượt được điểm tốt nhất trước đó), khác biệt lớn nhất đến từ Codebase (+20,6 điểm) trong khi Spectrum chỉ +2,9, và bài viết không tiết lộ phần cứng huấn luyện. [Nguồn: MarkTechPost](https://www.marktechpost.com/2026/11/19/meta-fair-self-improving-memory-harness-distillation/), [Hugging Face](https://huggingface.co/blog/).

* **Google đưa "Tool Retrieval" vào Gemini API — agent chỉ nạp schema của tool khi thật sự cần, thay vì nhét toàn bộ schema vào mọi prompt:** Tính năng đang ở bản preview trong Gemini Interactions API. Cơ chế: đặt một tool tên `tool_search` và bật `defer_loading: true` cho các tool muốn nạp theo yêu cầu; model ban đầu chỉ thấy tên và mô tả của các tool bị hoãn, và trong cùng một lượt API, model gọi `tool_search` để yêu cầu một tool, API nạp đầy đủ schema của tool đó rồi model phát ra lệnh hàm. Các bước truy hồi được ghi lại trong `interaction.steps` (gồm lệnh tìm kiếm, kết quả và lệnh hàm cuối). Phía server không cần xây hay hosting chỉ mục tìm kiếm riêng; với MCP server từ xa, bật `defer_loading: true` sẽ nạp toàn bộ tool mà server đó expose. Phía client thì đặt `"execution": "client"` và tự trả schema phù hợp qua `function_result` — tool không cần khai báo trước và có thể thêm mới giữa cuộc hội thoại, đổi lại mỗi lần tìm kiếm tốn thêm một round-trip. Điểm cần lưu ý về chi phí: bài viết không công bố con số tiết kiệm token cụ thể, chỉ nói giảm input token và độ trễ; schema đã nạp được tính tiền như input token cho phần còn lại của cuộc hội thoại, và `tool_search` bản thân nó cộng thêm một lượng input token cố định — nên lợi ích chỉ xuất hiện khi chi phí schema không bao giờ được nạp lớn hơn chi phí schema thực sự truy hồi. Hỗ trợ Gemini 3.6 trở lên, toàn bộ model Gemini 4 và Gemini Interactions API. [Nguồn: Google](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-tool-retrieval/).

Về failover: model được giữ nguyên, chỉ đổi hạ tầng triển khai — một request Claude lỗi ở Anthropic có thể do AWS Bedrock phục vụ; kích hoạt failover là lỗi nhà cung cấp, rate limit và timeout; request sai định dạng hoặc vượt context trả HTTP 400 và không retry; nếu mọi triển khai đều thất bại thì API trả HTTP 429 kèm Retry-After; request hỏng trước khi sinh đầu ra không bị tính phí; và người dùng không tự chọn được hạ tầng.
